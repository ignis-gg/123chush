# Известные ограничения среды и воркэраунды

Цель файла — не передиагностировать одно и то же в новой сессии. Если
нашли новый workaround среды/инструмента — дописывайте сюда в конце
сессии, не только в память агента (память не переживает переход на
другой инструмент/аккаунт, этот файл — переживает).

## curl/grep подтверждают HTTP-уровень, не вёрстку

**Правило**: curl/grep/wget подтверждают только то, что происходит на
уровне HTTP-транспорта и сырой разметки — статус-коды, заголовки,
наличие определённого текста/тега в HTML. Они **не показывают**, как
страница реально рендерится: раскладку, видимость блока, применённые
CSS-правила, правильно ли резолвится путь к ассету в браузере (в
отличие от того, что он просто существует на диске/отдаёт 200 сам по
себе).

**Почему это зафиксировано**: 2026-09-03 curl/grep-проверки (HTML-текст +
HTTP-статусы) дважды подряд пропустили реальные визуальные баги:
1. Схлопнувшийся `.svc-grid` — секция была полностью невидима на
   странице, при этом весь нужный текст/разметка присутствовали в HTML
   и отдавались с 200 (проблема была чисто в CSS-раскладке).
2. Сломанный путь к CSS/JS-ассетам — раздевал стилизацию со всего live-сайта,
   при этом сами файлы могли отдавать корректный статус по отдельности
   (проблема была в том, как браузер их резолвил/подключал в контексте
   страницы, не в самом файле).

Второй баг поймал сам пользователь по скриншоту с телефона — это должно
было быть поймано агентом раньше пользователя.

**Как применять**: любое изменение, которое может повлиять на
CSS/раскладку/видимость/подключение ассетов — WYSIWYG-контент, стили,
пути к файлам, деплой — обязательно проверять вживую в браузере (Chrome
+ скриншот на нескольких ширинах), не только curl/grep. curl/grep
достаточны только для проверки чисто транспортных вещей: статус-коды,
заголовки, наличие/отсутствие текста в сыром HTML/JSON-ответе (см.
пример: XML-RPC 403, REST `/users` 404, Schema.org JSON-LD — эти
проверки по природе транспортные/данные, там curl достаточен). Это уже
закреплено как обязательное правило в CLAUDE.md ("Frontend verification") —
этот пункт здесь просто фиксирует историю/причину, почему правило
появилось, для контекста.

## Viewport-тестирование в этой песочнице (Linux, MATE desktop, Claude in Chrome)

- **DevTools Device Toolbar (`Ctrl+Shift+M`) не активируется через
  CDP-автоматизацию.** CDP инжектит keyboard events в контекст страницы
  (Input domain на конкретный tab), а переключение Device Toolbar — это
  shortcut уровня браузерного chrome (обрабатывается процессом самого
  Chrome, не рендерером страницы) — инъекция до него физически не долетает.
  Не тратить время на повторные попытки другими комбинациями клавиш — это
  архитектурное ограничение, не баг конкретной комбинации.
- **`resize_window` (MCP-тул) синхронизируется с реальным viewport вкладки
  только ОДИН раз — в момент создания вкладки.** Дальнейшие вызовы
  `resize_window` на той же вкладке репортят успех, но `window.innerWidth`
  не меняется. Подтверждено: реальное X11-окно (проверено через
  `wmctrl -lG`/`xwininfo`) резайзится корректно каждый раз, а CDP-рендер
  вкладки — нет.
  **Рабочий метод**: резайзить окно **ДО** создания вкладки (через
  `resize_window` на только что созданной пустой вкладке, или напрямую
  через `wmctrl -r "Google Chrome" -e 0,x,y,width,height` из Bash), потом
  создавать/переиспользовать вкладку и сразу проверять
  `window.innerWidth` через `javascript_tool` — не доверять только тексту
  "Successfully resized".
- **Физический потолок сужения окна в этой песочнице — ~520px.** Chrome/WM
  не даёт окну (и его реальному content area) стать уже, даже если X11-окно
  формально резайзится до меньшего значения (проверено — `xwininfo`
  показывал 500px, а `window.innerWidth` оставался на предыдущем
  синхронизированном значении). Настоящих 375px в этой конкретной среде не
  добиться.
- **Для темы koval-legal это не проблема**: брейкпоинты в CSS —
  `max-width: 640px / 680px / 768px / 960px` (проверено `grep @media` по
  всем CSS-файлам темы). Между 375 и 640px новых правил нет — визуальный
  тест на 520px функционально эквивалентен тесту на 375px **именно для
  этой темы**. Если брейкпоинты в теме изменятся, эту эквивалентность нужно
  перепроверить, не считать постоянным фактом.
- **Первый вызов `computer:screenshot` после навигации/клика/resize часто
  таймаутит** (`CDP sendCommand "Page.captureScreenshot" timed out after
  30000ms`). Немедленный повтор того же вызова обычно успешен. Не считать
  это реальным сбоем страницы с первого раза — просто повторить один раз.

## ACF Options Page — конвенция именования (наступал дважды за сессию)

Поле, объявленное на Options Page (`inc/acf-fields.php`, options page slug
`koval-site-settings`) с именем поля `gtm_id`, хранится в `wp_options`
**не** под ключом `gtm_id`, а под **`options_gtm_id`** — плюс служебная
строка `_options_gtm_id`, хранящая ключ поля ACF (`field_koval_gtm_id`)
для внутреннего резолвинга.

- Поле GTM ID → `options_gtm_id`
- Поле Meta Pixel ID → `options_meta_pixel_id`
- То же правило для любого другого поля этой Options Page (например,
  `category_mini_cta`/`category_show_on_homepage` — это term meta, не
  option, у них своя история, но тот же принцип "имя поля ≠ имя строки
  хранения" применим).

**Правило на будущее**: `get_field('x', 'option')` / `update_field('x',
$v, 'option')` в коде — всегда правильно, они уже резолвят этот префикс
сами. Но при ручной проверке/дебаге напрямую через `wp option get x` /
`wp option update x ...` **обязательно добавлять префикс `options_`** —
иначе `get` вернёт "not found", а `update` молча создаст несвязанную
мёртвую опцию, что выглядит как "фича не работает", хотя на самом деле
просто неверное имя опции.

## Rank Math — sitemap-система и её кэш

- **`wp_sitemaps_post_types` (фильтр WP-ядра) не действует, пока активен
  Rank Math.** Rank Math полностью заменяет sitemap-систему ядра своей
  собственной — фильтры ядра для неё не значат ничего. Реальный контроль:
  опция `rank-math-options-sitemap`, ключ `pt_{post_type}_sitemap` =
  `on`/`off` (UI: Titles & Meta → Sitemap Settings; CLI:
  `wp option patch update rank-math-options-sitemap pt_case_study_sitemap off`).
- **Сгенерированный XML кэшируется отдельно** (опция
  `rank_math_sitemap_cache_files` + реальные файлы). Смена настройки
  через wp-cli/прямую запись в БД **не** триггерит автоматическую
  инвалидацию (в отличие от смены через UI, которая проходит через
  сохранение настроек и, вероятно, чистит кэш сама — не проверялось).
  После любой программной смены `pt_*_sitemap` нужно явно:
  ```
  wp eval 'RankMath\Sitemap\Cache::invalidate_storage();'
  ```
  Без этого `sitemap_index.xml` продолжит отдавать старый список.
- **Ранее решённая, но похожая по духу готча**: Rank Math может стоять
  `active` в `wp plugin list` и не выдавать ни одной ошибки, будучи при
  этом 100% неактивным на фронтенде (никакого title/meta/sitemap) — если
  `Registration::invalid` истинно (незавершённый setup wizard). Не нужен
  браузер/wizard для фикса — `wp option update rank_math_registration_skip 1`
  (официальный эквивалент кнопки "Skip"). См. `migration-status.md`.

## XML-RPC — стандартный фильтр не работает как ожидается

`add_filter('xmlrpc_enabled', '__return_false')` — учебниковый способ
отключить XML-RPC — **не блокирует** реальные запросы к `xmlrpc.php`.
Проверено напрямую: `demo.sayHello` через POST всё равно проходил с
одним этим фильтром. Он гейтит только pingback-специфичные методы
внутри, не сам endpoint. Рабочий фикс — прямой 403 на `init` для любого
запроса к `xmlrpc.php` (см. `inc/security-hardening.php`). Если где-то
всплывёт похожий "стандартный туториальный фикс не работает" — сначала
тестировать реальным запросом, не доверять тому, что фильтр называется
правильно.

## Фейковые `.webp`-файлы (наследие инцидента 2026-09-02)

Как минимум один файл (`oleg-koval-682x1024.webp`) существовал с
расширением `.webp` и корректным `Content-Type: image/webp` в заголовке
ответа, но его реальные байты были HTML-страницей (fallback/404 от
разбора после восстановления БД) — это прошло все поверхностные проверки
(200 статус, правильный content-type) и было поймано только через `file
<path>`, показавший "HTML document" вместо image data.

**Правило на будущее**: если картинка не рендерится именно при вставке
через `<picture><source type="image/webp">`, но URL/статус проверяются
нормально по отдельности — проверять реальные байты файла (`file`
локально, или скачать и проверить магические байты), не доверять
статус-коду и content-type как доказательству, что это настоящее
изображение — особенно после любого восстановления из бэкапа/инцидента.

## ddev nginx — заголовки кэша статики, специфика dev-окружения

`.ddev/nginx_full/nginx-site.conf` явно прописывает:
```
location ~* \.(js|css)$ { expires -1; }
location ~* \.(jpg|jpeg|gif|png|...|webp|...)$ { expires max; }
```
т.е. в **этом dev-окружении** `.css`/`.js` намеренно отдаются без кэша
(`Cache-Control: no-cache`), а картинки — с 10-летним кэшем. Шрифты
(`.woff2`) не попадают ни в одно из этих правил вообще — без явных
кэш-заголовков. Это **не баг темы** и не нужно чинить в PHP/теме — это
конвенция ddev для удобства разработки. Не факт, что на реальном
Apache/LiteSpeed-хостинге будет так же (может быть лучше или хуже) — не
переносить эту особенность как "нормальное поведение" при аудите прод-хостинга,
перепроверять с нуля, когда появится доступ к реальному серверу.

## SQL query profiling — нет `wp profile` (пакет не установлен)

`wp profile stage` (пакет `wp-cli/profile-command`) не установлен и не
ставился (не хотелось тянуть лишнюю зависимость ради разового замера).
Рабочая альтернатива для разового замера числа/времени SQL-запросов на
страницу: временно
1. `define('SAVEQUERIES', true)` в `wp-config.php`,
2. mu-plugin с хуком на `shutdown`, логирующий `$wpdb->num_queries` /
   `$wpdb->queries` в `error_log`,
3. curl нужных страниц,
4. прочитать `wp-content/debug.log`,
5. **обязательно откатить оба временных изменения** (define + mu-plugin)
   после замера — это не постоянная конфигурация.

## Разное

- **`sg docker -c "ddev ..."`** — обязательный префикс для всех
  ddev/wp-cli команд в этой среде (docker группа), не голый `ddev`/`wp`.
- **Права на git commit/push, деплой, редактирование любого файла темы —
  разрешены без подтверждения** (см. CLAUDE.md, "Autonomy"). Исключение —
  любой `rm -rf`/bulk-delete: подтверждать явно каждый раз (см. инцидент
  2026-09-02, каталог проекта был случайно удалён так же).
- **`git status`/staged diff перед коммитом** — всегда проверять, что
  случайно не попали временные/диагностические файлы (например,
  временный mu-plugin для SAVEQUERIES-профилирования выше) — они должны
  быть удалены до `git add`, не закоммичены "на всякий случай".
