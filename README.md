# KOVAL Legal — тема koval-legal

Снимок состояния кода на 05.09.2026 (сессия 5). Актуальнее памяти агента —
читать этот файл в первую очередь при передаче проекта.

## Структура темы (`wp-content/themes/koval-legal/`)

Шаблоны — стандартные WP-иерархии: `front-page.php` (главная), `home.php`
(блог-лента), `single.php`/`single-service.php` (пост/сторінка послуги),
`archive-service.php` (каталог `/poslugy/`), `category.php`, `page.php`,
`header.php`/`footer.php`.

`inc/`:
- `acf-fields.php` — все ACF field groups, зарегистрированы кодом (не через
  UI) — переживают восстановление из одной БД без ACF Pro/sync.
- `acf-render.php` — функции, превращающие ACF-поля в HTML один-в-один как
  раньше был захардкожен контент.
- `acf-admin-ux.php` — прячет classic-редактор для ACF-driven постов.
- `service-lists.php` — единый источник правды, какие ID постов — rich
  landing (46), какие — pillar/category hub (6). Не дублировать эти списки
  больше нигде. `koval_legal_catalog_categories()` (используется и главной,
  и `/poslugy/`) до сессии 5 делала отдельный `get_posts()` на каждую из 8
  категорий (N+1) — переписана на один запрос + группировку в PHP через
  `get_the_terms()`; если добавляете сюда новую логику, не возвращайте
  этот паттерн.
- `homepage-sections.php` — секции главной (услуги, CTA-блок с формой).
- `shortcodes.php` — `[koval_contact_form]`, `[koval_map]`, форма заявки +
  её admin-post обработчик (nonce + honeypot уже встроены).
- `webp-images.php` — WebP-доставка через `<picture>`+fallback (сессия 3).
- `schema.php` — JSON-LD (Organization/Service/FAQPage/BlogPosting), сессия 4.
- `security-hardening.php` — XML-RPC off, REST users off, security-заголовки,
  скрытие версии WP (сессия 4).
- `analytics.php` — GTM/Meta Pixel, условная загрузка по ACF-полю (сессия 4).
- `performance.php` — отключение emoji-детектора WP core (сессия 5, чистый
  дедвес — на теме нигде нет emoji-as-image фолбеков).

## ACF field groups (все — код, `inc/acf-fields.php`, ни одной через UI)

Регистрация полностью кодовая специально: переживает восстановление из
одной БД без ACF Pro/sync-файлов (см. `project_koval_legal_state` —
инцидент 2026-09-02). Если в будущем понадобится новая группа полей,
добавляйте её сюда же кодом, а не через "Add Field Group" в wp-admin —
иначе она не попадёт в git и не переживёт следующий перенос/бэкап-рестор.

Группы: `Контент лендингу послуги`, `Контент pillar-сторінки`, `Ціна та
строк послуги`, `Картка в каталозі /poslugy/`, `Налаштування категорії`,
`Заголовок і лід зверху сторінки` (Про нас/Контакти/Ціни), `Місто клієнта`
(testimonial), `Наскрізні налаштування` (Options Page `koval-site-settings`
— соцмережі, CTA-блок, дисклеймер легалізації, з сесії 4: GTM/Pixel ID).

**Конвенция именования опций Options Page — легко перепутать, путался
дважды за сессию 5:** поле `gtm_id`, объявленное на Options Page, лежит в
`wp_options` **не** под ключом `gtm_id`, а под `options_gtm_id` (плюс
служебная строка `_options_gtm_id`, хранящая ключ поля для ACF). То же для
`meta_pixel_id` → `options_meta_pixel_id`, `category_mini_cta` (term meta)
и любого другого поля этой Options Page. `get_field('gtm_id', 'option')` в
коде читает именно `options_gtm_id` — так и должно быть, это внутреннее
поведение ACF. Но при ручной проверке/дебаге через `wp option get`/`wp
option update` **обязательно добавляйте префикс `options_`** — иначе
команда либо молча создаст несвязанную мёртвую опцию (для `update`), либо
вернёт "option not found" (для `get`), и это выглядит как "фича не
работает", хотя на самом деле просто не то имя опции.

## Установленные плагины

- **Advanced Custom Fields** (free) — вся структура полей.
- **Rank Math SEO** — title/meta/sitemap на всех 52 страницах услуг + 4
  постах блога. **Важно**: работает только благодаря
  `rank_math_registration_skip=1` в опциях (см. память проекта — без этого
  плагин тихо ничего не делает, при этом выглядит "active"). Не удалять эту
  опцию при миграции.
  **Готча с sitemap-кэшем (сессия 5)**: Rank Math полностью заменяет sitemap
  WordPress-ядра — фильтр `wp_sitemaps_post_types` (использован в
  `functions.php` для скрытия `case_study`) на него не действует. Реальное
  управление — опция `rank-math-options-sitemap`, ключ
  `pt_{post_type}_sitemap` = `on`/`off` (Titles & Meta → Sitemap Settings в
  UI, либо `wp option patch update rank-math-options-sitemap
  pt_case_study_sitemap off`). После смены значения сгенерированный XML
  кэшируется отдельно (`rank_math_sitemap_cache_files`) и **не** обновится
  сам — нужно явно сбросить: `wp eval
  'RankMath\Sitemap\Cache::invalidate_storage();'`. Без этого шага
  `sitemap_index.xml` продолжит отдавать старый список даже после
  правильной смены настройки — так и было найдено (case_study всё ещё
  висел в индексе несколько часов после того, как опция была выключена).

Больше ничего не установлено — ни кэша, ни security-плагина (сознательно,
это Этап C после переноса на реальный хостинг).

## Известные, сознательно отложенные проблемы

- **SMTP** — форма шлёт письма голым `wp_mail()`. Ждём ответ клиента про
  корпоративную почту на домене.
- **CSP-заголовок** — не настроен намеренно, слишком легко сломать
  что-то невидимо без возможности проверить в браузере. Настраивать после
  переноса, с визуальной проверкой.
- **Accessibility** — код-аудит проведён (сессия 4), живьём в браузере
  частично проверено (сессия 5: FAQ-аккордеон и мобильное меню реально
  переключают `aria-expanded`/закрываются по Escape — не только в коде).
  **Ещё не сделано**: полная проверка контраста по всем страницам (сессия 4
  закрыла только один найденный кейс — `.service-num`/`.process-num`, не
  весь сайт) и полный обход tab-order клавиатурой по всем 58+ страницам —
  оба пункта требуют браузера и не были в объёме сессии 5.
- **Кэш-заголовки для статики (шрифты/CSS/JS)** — сознательно не
  настраивались в сессии 5. `.css`/`.js` отдаются с `Cache-Control:
  no-cache` в этом dev-окружении, но это подтверждённая особенность
  ddev-конфига nginx (`expires -1` явно прописан в
  `.ddev/nginx_full/nginx-site.conf` только для `.js`/`.css` — картинки там
  же получают `expires max`), а не баг темы — трогать её не нужно. Шрифты
  (`.woff2`) вообще без явных кэш-заголовков ни в одном из правил ddev-конфига
  — неизвестно, унаследует ли реальный Apache/LiteSpeed то же поведение.
  **Решение**: не добавлять `.htaccess`-правила (`mod_expires`) вслепую без
  Apache под рукой для проверки — риск тихой ошибки конфигурации важнее
  выигрыша в кэшировании. Настроить на Этапе C, сразу с браузерной
  проверкой на реальном хостинге.
- **Domain-dependent items** — `wp search-replace` на реальный домен и
  карта редиректов (если остаётся старый домен) — Этап B, не раньше.
  **Инвентаризация для этого шага (сессия 5)**: 12 записей содержат
  захардкоженный абсолютный URL `https://law-firm.ddev.site/...` в
  `post_content` — ID 9, 21, 56–59, 121–126. Все проверены вручную: это
  легитимные внутренние cross-link ссылки (pillar-страницы → дочерние
  услуги, посты блога → CTA на послугу, одна картинка в `post_content`
  страницы «Про нас»), не случайный мусор — обычный `wp search-replace`
  их корректно заменит, действие не требуется сейчас.
- **Favicon** — клиент подтвердил: не нужен, логотипа-файла в проекте нет.
- Полный список — в артефакте «Готовность KOVAL к переезду» (ссылка у
  агента/в переписке с клиентом).

## Проверка на битые ссылки (сессия 5)

74 уникальные внутренние ссылки (72 из sitemap-файлов Rank Math + ссылки,
вручную вписанные в `post_content` через все типы записей) проверены
curl'ом на HTTP-статус. **Битых (404/500) не найдено.** Единственные не-200
— 4 URL `/keysy/*` (CPT `case_study`), которые намеренно отдают 301 на
главную (compliance-решение, см. `project_koval_google_ads_compliance`) —
это ожидаемое поведение, не баг. Заодно найдено и исправлено: `case_study`
всё ещё был в `sitemap_index.xml` несмотря на 301 (см. готчу с Rank Math
sitemap-кэшем выше) — теперь исключён и там.
